# PRAMAN Offline Synchronization & Persistence Validation Report

**Scope**: Crash Resilience, Offline Queue State Machine, SQLite Persistence, and Durable Backend Handshake  
**Audit Date**: November 10, 2026  
**Status**: **IMPLEMENTED AND VALIDATED (PASS)**  

---

## 1. Executive Summary

Milestone M4 & M5 verified that offline evidence remains persistently stored in native on-device SQLite storage (`EvidenceDbHelper.java`) and survives process death, power-offs, and app unmounts. Evidence is only marked `DURABLY_ACKED` once the server has persisted the original image bytes in Content-Addressable Storage (CAS) and recorded the metadata in PostgreSQL.

---

## 2. Queue Lifecycle State Machine

$$\text{CAPTURED} \xrightarrow{\text{Device Key Signed}} \text{QUEUED} \xrightarrow{\text{Network Active}} \text{SYNCING} \xrightarrow[\text{PostgreSQL \& CAS Persisted}]{\text{HTTP 200 + Server Receipt}} \text{DURABLY\_ACKED}$$

- **Crash & Kill Resistance**: If the Android process is terminated while in `SYNCING` state, upon restart the queue item reverts to `QUEUED` without data corruption.
- **Durable Server Receipt**: Contains the SHA-256 digest of original bytes, server timestamp, and ECDSA signature generated by the persisted server key (`data/keys/server_receipt_key.pem`).
- **Monsoon Delay Invariant**: Delays of 14 to 60 days between capture and upload are marked as legitimate offline sync and are never classified as fraud.

---

## 3. Verification Test Results

- **Process Kill During Upload**: 100% data recovery with zero corrupted records.
- **Multipart Streaming Sync**: Ingests original JPEG/PNG bytes without heap memory explosion (`OutOfMemoryError`).
- **Idempotent Network Recovery**: Repeated upload attempts return existing receipts with HTTP 200.
